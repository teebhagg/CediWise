Executive Summary

Apple does not expose an iOS API that lets an ordinary app scan a user’s Messages inbox or register an SMS receiver equivalent to Android’s READ_SMS and RECEIVE_SMS flow. Apple’s IdentityLookup framework is a narrow spam-filter extension: it receives a new SMS or MMS from an unknown sender for a filtering decision, excludes known contacts and iMessage, and restricts the extension from using the network directly or sharing a container with its app [1][2][3][4][5]. It cannot provide CediWise with an inbox reader.

Apple Shortcuts offers a workable, user-configured route for new messages. A personal automation can trigger on a received message, apply sender or text criteria, and run automatically; an action can then open a CediWise URL carrying the message content [6][7][8]. Expo Router supports custom-scheme links and query parameters, so CediWise can pass that message into the existing import service [11][12]. This route requires the user to create the automation, and opening the URL brings CediWise to the foreground for each matching message. It does not give the app a silent background SMS listener.

The current implementation adds an iOS opt-in, setup steps, a custom-link receiver on the import screen, and reuse of the existing authenticated importOneMessage flow. It imports only when the user has enabled tracking and the live-import feature flag is active. Incoming link content is limited to 4,000 characters and removed from route parameters before processing. Older messages still use manual paste. iOS 26 introduced a Shortcuts “Find Message” action, and iOS 27 adds message search actions, so historical import may be possible through a user-run Shortcut; that needs a separate batch handoff design and device validation [9][10].

This is source-level implementation work. No iPhone build or Shortcuts automation has been exercised yet. The key product constraint is clear: iOS can support consented, new-message import through Shortcuts, but it cannot match Android’s direct inbox scanning or background receive behavior.

Introduction

This research answers how CediWise can add iOS MoMo SMS import comparable to the current Android feature. The scope is platform access, a practical user experience, app integration, consent, and the next implementation gates. The comparison uses the existing CediWise Expo app as the baseline: Android has an inbox reader, an incoming-message listener, secure native queueing, and an import API; iOS currently has manual paste and a Shortcuts placeholder [14].

The main assumption is that the first iOS release should preserve the current MoMo parser, authenticated API, deduplication, and budget refresh behavior instead of creating a second transaction pipeline. A matching Shortcuts message should enter the existing import path only after the user opts in. The current iteration focuses on new incoming messages. Historical scans, deployment, and App Store review are later gates.

The method was a quick, primary-source review of Apple’s IdentityLookup documentation, Shortcuts user guides and release notes, App Store Review Guidelines, and Expo’s deep-link documentation. Claims about iOS access are stated as a conclusion from the documented API scope, not as a claim that Apple has published a single sentence saying “third-party apps cannot read the inbox.” The sources were retrieved on 2026-10-25. Product behavior described in this report is based on the current CediWise checkout, not a device test.

Main Analysis

1. Native inbox scanning has no supported app API

The Android flow uses Android-specific packages and native code to query inbox rows and receive new SMS events. In the current checkout, androidSmsReader.ts queries the inbox by date, androidSmsListener.ts subscribes to received messages, and native/momo-sms/ stores and retries captured events [14]. That model depends on Android SMS permissions and cannot be carried across to iOS as a React Native package substitution.

Apple’s documented message-content interface is IdentityLookup. Its request contains a sender and message body, but the request is explicitly for a message from an unknown sender [3][4][5]. Apple’s overview narrows the feature further: it applies to SMS and MMS from unknown senders, not messages from contacts or iMessage, and the extension’s purpose is to decide whether an incoming message is unwanted [1][2]. The extension cannot access the network directly and cannot write to a container shared with its containing app [1].

Taken together, those documents support a practical engineering conclusion: IdentityLookup is not an inbox-reading interface and cannot act as CediWise’s general-purpose importer. It may see some incoming payment alerts, but it cannot guarantee coverage of all provider senders, share the content with the main app through an app-group queue, or upload transactions from that extension. Building a spam-filter extension for expense capture would also use a feature for a purpose outside its documented job. The correct product boundary is to avoid describing iOS as reading or scanning Messages.

This limit changes parity expectations. Android can search a recent window and listen for events while the app is paused. iOS must receive selected messages through an Apple-supported handoff that the user configures. CediWise should keep manual paste available and name the iOS feature as Shortcuts import, rather than implying that the app has SMS permissions or inbox access.

2. Shortcuts supports a consented handoff for new messages

Apple documents a Message personal-automation trigger with sender and “Message Contains” criteria [6]. Message automations are eligible to run automatically, and Apple’s guide describes allowing them to run when the phone is locked [7]. That gives a user a way to select which new messages should be forwarded. The message trigger is broader than Ghanaian MoMo SMS, so CediWise still needs to validate the sender and body locally before sending a transaction to its API.

The proposed handoff uses the existing app scheme and Expo Router route /profile/import-sms. Expo documents that a configured custom scheme opens a route in the app and that query parameters can be read with useLocalSearchParams [11][12]. The automation encodes the message and sender into query values, then uses an Open URLs action [8]. This avoids putting a long-lived CediWise API token in Shortcuts and lets the app use its existing signed-in Supabase session through smsImportClient.ts [14].

The cost is visible foreground behavior: opening a CediWise URL launches or foregrounds the app. Apple’s documentation says message automations can run automatically, but does not promise that a third-party app opened by one will process a transaction invisibly or while locked. Therefore, the safe product statement is that Shortcuts can pass a matching message to CediWise and CediWise opens to process it. On-device validation must establish the exact locked-device behavior and whether the user sees an unlock or confirmation prompt.

The implementation checks local tracking consent and the existing release-time live-import feature flag before automatic import. If either is off, the message is placed in the existing paste field for a manual action. If both are on, CediWise invokes the same importOneMessage method used by Android’s live listener, which preserves the current candidate parsing, authenticated upload, deduplication, and budget refresh behavior [14].

3. Historical lookup may be possible through Shortcuts, but it is a separate path

Apple’s iOS 26 Shortcuts release notes list “Find Message” and “Find Conversation” actions for Messages [9]. The iOS 27 release notes add “Search in Messages app” and describe sender filtering for Find Message [10]. These features suggest a user-run Shortcut can search some existing conversation history, which means manual paste may not be the only future fallback for older texts.

The current evidence does not establish a direct inbox-reading entitlement for CediWise. The history search is an action inside the Shortcuts environment; its output still has to cross into the app. The new-message URL path can carry one message at a time, but repeatedly opening the app for every result would be a poor batch-import experience. A history feature should instead define a bounded date window, pass a small collection into one app handoff, run messages through the existing preview and deduplication path, and show a review step before writing expenses.

The current implementation hides Android’s “Message history” scanner on iOS and keeps paste available. This is deliberate: presenting a 2/7/30-day scan button when the app cannot query the inbox would overstate the capability. A later Shortcuts history prototype should be tested on the minimum supported iOS version and current iOS release, including the number of results, sender/date fields, URL size, duplicate behavior, and the way Shortcuts handles large result lists. Until then, CediWise should describe the implemented behavior as new-message automation plus manual paste.

4. Consent and handoff data need clear boundaries

The Shortcuts route carries message text in a URL query parameter. Expo supports query parameters as route input [11][12], and Apple’s Shortcuts URL documentation requires URL-encoded text when putting text into a URL [8]. That makes encoding and size checks part of the feature boundary. The implementation accepts at most 4,000 characters, removes the message and sender from route state as soon as it receives them, avoids logging their contents, and uses the app’s existing API path only after a user opt-in and the live-import kill switch both pass [14].

App Store Review Guidelines require explicit user permission for sharing app data and appropriate data security [13]. CediWise’s consent screen explains that the automation passes selected message text and sender details, that matching content may be processed by the import service and Supabase, and that import logs containing message text are retained for up to 180 days [14]. Users can turn the app-side setting off and must also remove or disable their personal automation in Shortcuts to stop the operating system from opening the app for future matches.

Because the app link can be opened by any source, it must be treated as untrusted input. Automatic import is gated by the local opt-in, the release flag, the authenticated API session, and the existing MoMo parser. Messages that do not match supported Ghana provider formats fail through the established import error path. The URL is not a replacement for authentication and does not contain credentials. The remaining operational question is whether CediWise should auto-add directly on iOS or present a review card when a Shortcut opens it; this iteration follows Android live-import behavior for eligible transactions, while keeping manual and ambiguous cases visible.

Synthesis & Insights

The best available iOS model is not a native SMS reader. It is a user-configured bridge: Shortcuts filters selected incoming messages, then opens CediWise with encoded content. This keeps CediWise’s server authentication and parser in the app while respecting Apple’s documented boundary around Message Filter extensions. It also gives the user control over the sender or text criteria.

The first implementation is materially narrower than Android. It supports new messages that the user routes through an automation, foregrounds CediWise for each accepted message, and does not scan history. Those limits are part of the product behavior and should appear in setup copy and privacy language. The shared parser and API reduce backend divergence, while the explicit local opt-in and release flag make the iOS route independently controllable.

Historical lookup is a promising second phase because Shortcuts has Messages search actions in current iOS releases. It should be treated as a separate batch import design rather than assumed to be a normal app permission. The route needs one bounded collection handoff and a review interface; the Android history UI should remain hidden on iOS until that path works.

Limitations & Caveats

The research relies on public Apple and Expo documentation and does not inspect private iOS APIs or App Store reviewer decisions. The conclusion that no Android-like inbox reader is available is an inference from Apple’s documented API set and IdentityLookup’s explicit scope. Apple’s Shortcut release notes identify message search actions but do not document every field, limit, permission prompt, or edge case in their output.

The custom-scheme route and current import handler have not been exercised on an iPhone. This report does not establish behavior when the device is locked, when CediWise is terminated, when an automation receives a non-SMS message, or when the user has not signed in. The current implementation also does not install a Shortcut automatically; users create the personal automation in Shortcuts.

The app’s existing import endpoint, session refresh, raw-message retention, and category/reversal rules are reused from source code. This report is not a backend security audit, App Store approval, privacy-law review, or proof of deployed feature-flag configuration. A device test and a privacy-policy review remain necessary before enabling the feature broadly.

Recommendations

Keep the native Android reader and iOS Shortcuts handoff as separate platform adapters over the shared MoMo parser and import API. Describe iOS as “Shortcuts import,” say that the user must create a Message automation, and state that CediWise opens for each matched message. Keep automatic import behind the existing release-time kill switch and require local opt-in before processing URL input.

The next device pass should use an iPhone development build. Test a valid MTN, Telecel, and AT Money alert; an OTP and an unrelated text; sender/content URL encoding; app cold launch and warm launch; duplicate delivery; sign-out; disabled opt-in; feature flag off; locked device; and network loss. Confirm that malformed or oversized query values do not reach the API and that route parameters are cleared after handoff.

After live-message behavior is proven, prototype historical import with the iOS 26+ Shortcuts Find Message action. Pass a small, date-bounded batch once, build review cards with the existing expense preview, and confirm deduplication against Android and manual imports. Do not describe historical scanning as available until that flow has been implemented and tested on supported devices.

Methodology Appendix

The question was scoped to supported ways to bring MoMo payment messages into an Expo app on iOS. Retrieval prioritized first-party Apple and Expo sources because API scope, automation behavior, URL handling, and current platform support can change. Triangulation used Apple’s IdentityLookup overview, extension-creation guide, request model, and sender/body properties; Apple’s Shortcuts trigger and automation guides; current Shortcuts release notes; and Expo’s app-link and route-parameter documentation.

The most important interpretation is that Shortcuts is an operating-system workflow the user configures, not an entitlement granted to CediWise. The recommended deep-link handoff is a design inference from Apple’s automation and URL features plus Expo’s documented route handling. The report does not claim App Store acceptance or device-level behavior. Research mode was quick, appropriate for initial implementation framing; no academic or market research was needed for this platform API question.
